# ISUCON14 ルールブックの要点

出典: isucon/isucon14 の docs/manual.md（当日マニュアル）と docs/ISURIDE.md（アプリケーションマニュアル）。
CLAUDE.md §2・§3 と矛盾する場合はこちらを優先する（今回、矛盾は無い）。

## 禁止事項

- CloudFormation テンプレートの内容に沿わなくなる変更（インスタンスタイプの変更など）をした環境で競技する（manual「競技環境」）
- セキュリティグループの SSH(22)・HTTPS(443) の変更。他のポートの開放は可（manual「競技環境の変更」）
- `envcheck.service` 関連（`/etc/systemd/system/envcheck.service`、`multi-user.target.wants/envcheck.service`、`/opt/isucon-env-checker`）、
  `isuadmin` ユーザー、`isucon` 以外のユーザーや既存の公開鍵、サーバーの再起動の妨害（manual「変更してはいけない点」）
- 競技終了時点で、ポータルのサーバーリストに複数のスタックが混在している（manual「複数スタックの問題」）
- 認められたサーバー以外に処理を委譲すること。モニタリング・テスト・開発・AI・外部のコンテナレジストリは可（manual「禁止事項」）
- 競技終了後、アナウンスまで競技環境に接続・操作すること（manual「競技環境」）

## 追試の条件

manual「追試」

1. 3 台を再起動する（1 台でも再起動できなければ失格。競技終了時に停止しているサーバーがあると失格）
2. envcheck が通ること
3. 3 台が同じ VPC に所属していること
4. 最終スコアを記録したサーバーに負荷走行。FAIL または最終スコアの 75% 以下なら再実行し、3 回目でも同じなら失格
5. 再度 3 台を再起動する
6. 負荷走行で書き込まれたデータが、再起動後に取得できること
7. フロントエンドにアクセスでき、構造がリファレンス実装と同じで、意図しないデータが表示されないこと

負荷走行の中身（manual「負荷走行」）

- `POST /api/initialize`（30 秒）→ オーナー・椅子・ユーザーの登録 → 整合性チェック → 負荷テスト 60 秒 → 最終チェック
- 負荷テストの終了時点で行われていた決済は、終了後 5 秒以内に完了すること。間に合わないと FAIL
- 次の場合は FAIL: 初期化中のエラー、クリティカルエラー、ワーニング 200 件以上、整合性チェックのエラー
- 初期化処理（`/api/initialize`）が行っている内容は、処理やデータ構造を変えても漏れなく提供すること（manual「データベースのデータの初期化」）

## スコアの計算式

manual「スコアの計算」

- 椅子がライドとマッチした位置から乗車位置までの移動距離の合計 × 0.1
- 椅子の乗車位置から目的地までの移動距離の合計
- ライド完了数 × 5

改善の指針（ISURIDE.md「ライド」「椅子」）

- 完了したライドの数と距離でスコアが決まる。ライドを多く・速く回すほど伸びる
- ライドの評価が高いとユーザーが増える。評価に効くのは、割り当てまでの時間、乗車位置に早く着きそうか
  （近い椅子、または遠くても速い椅子）、乗車までの時間、目的地までの時間
- 椅子のモデルごとに速度が違う。待ち時間と全体の流動性を考えて割り当てるのが望ましい
- オーナーは収益が十分だと椅子を増やす

## レスポンスの形の制約

- レスポンスの構造は変えない（CLAUDE.md §2）。追試ではフロントエンドの表示もリファレンス実装と比べられる
- 通知（`/api/app/notification`・`/api/chair/notification`）は JSON のポーリングでも SSE でもよい（ISURIDE.md「通知エンドポイント」）
  - どちらでも、状態が変わってから 3 秒以内に通知されること
  - すべての状態遷移を、発生した順に、少なくとも 1 回返すこと（前のライドの ARRIVED・COMPLETED → 次のライドの MATCHING… の順）
  - JSON の場合、クライアントは `retry_after_ms` の後に再度リクエストする（リファレンスは 30ms）
  - SSE の場合、`Content-Type: text/event-stream`、`data: <JSON レスポンスの data と同じ JSON>` を 1 行で。接続したら即座に最新の状態を送る
- `GET /api/internal/matching` と `isuride-matcher.service` は内部用なので、自由に仕様を変えてよい（ISURIDE.md「ライドのマッチング」）
- 決済サービスは `Idempotency-Key` ヘッダに対応している。同じキーのリクエストは冪等に処理される（ISURIDE.md「決済マイクロサービス」）
- 猶予時間（manual「猶予時間」）
  - `GET /api/app/nearby-chairs` の座標は、過去 3 秒以内に `POST /api/chair/coordinate` で送られた座標と一致すること
  - `GET /api/owner/chairs` の移動距離の合計は、3 秒以内に反映されること
  - マッチされたライドは、30 秒以内にユーザーと椅子に通知されること
- ベンチマーカーのタイムアウト: `/api/initialize` 30 秒、通知 2 種 60 秒、それ以外 10 秒（manual「ベンチマーカーのタイムアウト」）
