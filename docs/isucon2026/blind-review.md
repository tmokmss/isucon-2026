# 方針を見せずに改善策を出させた結果（競技後）

スキル isucon-improve の「頭打ちを疑うとき」の手順で、競技後に 2 本のエージェントに改善策を出させた。渡したのは最終版（eb573db）の webapp/go・conf・docs/RULEBOOK.md・docs/MANUAL.md、最終版のランの report.md（note の行と前回との差分の節を削ったもの）・bench.log、asia1 と asia2 の CPU プロファイル、台の種類と距離の説明だけ。ラン記録・試作の履歴・振り返りの Issue は渡していない。問いは「律速を特定し、一番重い処理を減らす方法を置き場所・計算の仕方（SIMD・まとめての計算・ライブラリ）・回数の観点で全部挙げ、スコアの式から見た攻めどころも挙げる」。

## スコアの式から見た指摘

- Opus: europe・america は毎日約 2.9 倍に増えたのに、asia だけ 4 日目→5 日目が 1.54 倍（413 → 636 人）。asia が 2.9 倍に伸びれば、5 日目と最終日の加点が約 25% 増える
- Codex: 最終日の人数 × 倍率は asia 637、europe 844.5、america 474 で、asia 以外が 67%。asia を直した後は、倍率 1.5 のリージョンを崩さないことを優先する

## Opus の出力

**結論**: 律速は asia2（PostgreSQL と asia の読み取りを返す複製アプリが同居している台）の CPU です。CPU の半分を画像URLの署名計算が使っており、これを減らして asia の利用者の伸びを取り戻すのが最大の攻めどころです。

**律速の根拠**
- asia2 は CPU 平均70%で、90%以上の時間が61%（isureal が116%）。他の3台は29〜34%で余っています
- asia2 の pprof（20秒）の内訳は、HMAC を1000回重ねる署名（computeImageSignature）が47%、GC が約27%、JPEG 検証の受け持ちが8%です
- 人数の伸びは europe・america が毎日約2.9倍なのに、asia だけ4日目→5日目が1.54倍（413→636人）。asia は4日目にエラーか遅延が出ています。2.9倍に伸びれば約1,200人になり、5日目と最終日の加点が概算で約25%増えます

**効きそうな順**
1. **asia2 の署名を他台に計算させる**（env だけ・小）。asia2 には ISUREAL_OFFLOAD_PEERS が無く、Memories（25%）とエクスポート（22%）の署名をすべて自分で計算しています。europe・america を計算先に足し、asia2 は JPEG 検証の受け先から外します。代わりに往復100msが応答に乗ります。
2. **同じ署名の二重計算をやめる**（小〜中）。asia2 が作ったURLの署名を、asia1 が `/api/images/` の検証で別のキャッシュから計算し直しています。asia1 の旧プロファイルでは、この画像取得の処理が22%でした。画像の GET も asia2 に回すか、asia2 が計算した署名を asia1 に複製します。
3. **HMAC を自前で書く**（小）。鍵の前処理（ipad/opad）の中間状態を1回だけ作り、1反復を SHA-256 の圧縮関数2回の直接呼び出しにします。署名計算18.3秒のうち、SIMD の本体（blockAVX2）以外の4.7秒（26%）が消えます。
4. **複数の画像をまとめて SIMD で計算する**（中〜大）。c5 は AVX-512 が使えるので16画像を並べて計算します（単一計算の4〜6倍。記憶から書いた値）。isa-l_crypto の sha256_mb を cgo で呼ぶか、Go のアセンブリで書きます。Memories・エクスポートは既に署名対象をまとめているので、そのまま渡せます。フィードは呼び出しをまとめる改修が要ります。
5. **次の分の署名を先に計算しておく**（中）。exp は次の分で決まるので、直前1分に返した画像の次の分の署名を europe・america に分の境目より前に計算させ、全台に配ります。これらの台は SHA-NI を持ち、CPU は約30%しか使っていません。あわせて exp を画像ごとに「ID のハッシュ % 60秒」だけずらし（+59秒以内に収まる）、境目での一斉再計算をならします。
6. **GC を減らす**（小〜中）。署名キャッシュの `map[string][]byte` を、固定長のキーと `[32]byte` の値を持つポインタ無しの map にし、古い exp の分から捨てます。asia2 は GOMEMLIMIT=1200MiB に対して空きメモリが最小101MB です。
7. **asia の GET を asia1 と asia2 で重み付けして分ける**（nginx・小）。asia1 は CPU 34% です。
8. **exp の丸めを2分にする実験**（小）。再計算の回数が半分になります。ただし5分でFAIL、1分で合格しており、2分は未確認なのでFAILのおそれがあります。

**規約**: 1〜7は URL・応答の形・署名の検証結果を変えず、計算先も競技サーバの中なので触れません。8は exp の範囲検証で失敗するおそれがあります。

**配点から見た攻めどころ**: エクスポート（20点）と最後の投稿期間のフィード検証（20点）の配点が大きく、エクスポートは asia2 の負荷の22%を占めます。europe・america は倍率1.5ですが既に最大のペースで伸びているので、asia が伸びて asia1 の負荷が増えても崩さないことが条件です。

**ほか**: PostgreSQL では画像をまとめて取るクエリが平均276msかかり、遅いクエリの合計時間の43%を占めます。ただし asia2 の CPU では postgres は16%で、律速ではありません。

## Codex の出力

結論：律速は asia2（isu4）のGo。最終ランは台CPU平均70.1%、90%以上61%、isureal 116%（postgres16%）。他台は平均28.8～34%、アプリ45～53%。別採取20秒pprofも38.88 CPU秒＝192%で、画像URL署名18.30秒/47.1%（SHA本体13.57秒/34.9%）が首位。GC scan 26.8%、malloc 18.6%、assist 16.9%は累積値。通知503×6、EOF×2も飽和と整合する。

効く順（効果は重複）：

1. asia2の署名をレスポンス単位で集めて重複排除し、近いasia1（:8090を起動）→空くeurope/americaへ一括offload。feed/RealMoji/関係一覧にもMemories同様のprefetchを入れ、重いasia GETはasia1/2へ重み付き分散。全移送のAmdahl上限1.89倍、平準化は約2倍余地。既存ルーター経由なら規約内、S3/CDN不可。中。
2. 回数削減：完成URLを(imageID,exp)で2世代キャッシュ、要求内memoize、HasMore判定用51件目は署名せず、次分を低優先度生成、生成側・画像検証側で共有。47%のmiss/分境界の山が対象。期限・形式・1000回HMAC維持で規約内。中。
3. 計算法：鍵別inner/outer SHA状態を前計算した固定長HMAC専用実装＋複数件AVX2 multi-buffer（Intel IPsec Multi-Buffer/ISA-L Crypto、OpenSSL EVPを実測比較）。4倍なら全体1.35～1.55倍。c7iはGoのSHA-NIを使う。完全一致試験必須、規約内。大。
4. export画像はinit/newを先に読み、DBならidのANY一括＋EXPLAIN後に(id,created_at)索引。現状203回56.017秒、全SQLの43.3%、平均276msをほぼ除去し得る。画像同一なら規約内。中。
5. URL/author応答共有、slice正確予約、JSON/buffer pool、compact/shard cacheで割当削減。GC上限約27%。その後だけGOGCを上げる（free最小101MB、先行はOOM危険）。規約内。中。
6. JPEGをasia1→飽和asia2へ投げずasia1 local→c7i順にする。asia2の4.84%、asia1の7.57%が対象で投稿→友達feedを守る。別ライブラリは全入力で現checkerと一致時のみ。規約内。小。
7. 初期全表を永続snapshot/asia1一括配布＋差分化。posts16.774秒、RealMoji24.524秒、comments8.694秒、rebuild6.62秒を削る。得点より60秒初期化・追試向け。耐久・再起動・initialize維持で規約内。大。
8. 配点上はログイン/投稿/友達feed（10、最終20）を最優先、次にexport20、RealMoji/退会5、comment/profile/Memories月3。閲覧上限は1人・期間ごとにfeed20、画像4×2点、詳細8、一覧8、profile4なので達成までのreadを短縮。最終人数×倍率はasia637、europe844.5、america474で非asia67%；asia解消後は1.5倍地域を優先。503は直接減点なしでも再試行が性能判定に残る。規約内、実装なし。
