# DB を捨ててインメモリ化する

ISUCON14 のリハーサル（[isucon-harness#18](https://github.com/tmokmss/isucon-harness/issues/18) ）で、
MySQL を捨てて全状態をメモリに持つ実装に書き換え、2,034 → 82,363 まで伸ばした。
そのとき踏んだ落とし穴と判断をまとめる。

**参照実装**: ブランチ `rehearsal/isucon14` の `webapp/go/store.go`（ストア・永続化・シグナル）と
`webapp/go/initial_data.go`（mysqldump のパーサ）。

改善の回し方そのもの（1 周 1 変更・計測・採否）はスキル `isucon-improve` に従う。
インメモリ化は変更が大きいので、**1 周で入れてよいが、必ず再起動試験まで通してから採用する。**

## 0. やるかどうか

先に `docs/RULEBOOK.md`（当日マニュアルの要点）を確かめる。特定のミドルウェアの利用や、
採点時に DB を見るといった条件があれば、やらない。

| 条件 | 判断 |
|---|---|
| 状態が小さく（数十 MB まで）、全体を 1 プロセスで持てる | **MySQL を捨てる**（この文書のやり方） |
| 状態が大きい / SQL で分析したい / 初期化が SQL に強く依存する | MySQL を残す。読み込みはメモリ、書き込みは順序を保った非同期（FIFO で 200ms ごとにまとめて書く等） |
| アプリを複数台に分けないと CPU が足りない | 状態を持つプロセスは 1 つのまま。他の台に nginx などの状態を持たない処理を逃がす |

- **状態を持つプロセスは 1 つだけにする。** 複数台で同じ状態を持つと、台同士の不整合と
  編集の競合が起きる。nginx は、状態を持つ 1 台にだけ振る
- 捨てる根拠は計測で示す（例: slow query の上位を DB が占め、CPU は mysqld が大半）

## 1. データ構造

- **ストアは 1 つの構造体にまとめ、`sync.RWMutex` を 1 つ持たせる。** 書き込みは `Lock`、読み込みは `RLock`
  - 「読んでから書く」処理は、1 つのロックの中で完結させる（更新が失われないように）
  - **外部呼び出し（決済 API など）の間はロックを放す。** 戻ってから状態を確かめ直して書く
  - ロックの中の処理がマイクロ秒単位なら、ロック 1 つで十分速い。スループットが頭打ちになったら分割を考える
- **元の SQL を 1 本ずつ書き出し、それぞれに対応する map / slice を用意する**
  - `WHERE x = ?` → `map[x]` / `ORDER BY created_at` → 作成順に append した slice / `LIMIT 1` → slice の端
  - 同じ時刻の行の並び（`ORDER BY` の同順位）は、挿入順 + ID で決める
- **履歴を全部持たない。** API が読むのが集約だけなら、集約だけを持つ
  - 例: `chair_locations` は全件を持たず、椅子ごとに「最新の位置・累計距離・最終更新時刻」だけを持つ。
    重い集計クエリ（slow query の 65%）が O(1) になった
- ロックの外で使う値（レスポンスに詰める値）は、ロックの中でコピーしておく

## 2. レスポンスの互換（変えると失格）

レスポンスの構造体は元のまま使う。そのうえで、SQL と Go の挙動の差を 1 つずつ潰す。

- **`nil` と空の slice の違い**: 元が `var xs []T` に append する書き方なら、0 件のとき JSON は `null`。
  `[]T{}` にすると `[]` になり、形が変わる
- **並び順**: `SELECT * FROM t` は主キー順（ULID なら作成順）。Go の map を回すと順序がばらばらになる。
  元の順序が不定だった箇所（元も map を回していた等）は不定のままでよい
- **時刻**: `CURRENT_TIMESTAMP(6)` はマイクロ秒で丸まる。`time.Now().UTC().Truncate(time.Microsecond)` に揃える。
  `UnixMilli()` で返す値がずれないように
- **`ON UPDATE CURRENT_TIMESTAMP`**: 行が実際に変わったときだけ `updated_at` が進む。同じ値の UPDATE では進まない
- **エラーの返し方**: 一意制約の違反は元のコードでは 500 になる。同じステータスを返す
  （検証を先にしてから書く。元はトランザクションで巻き戻していた）
- 元が `/initialize` 後に `settings` を読んでいた値（決済の URL 等）もストアに持つ

## 3. 初期データと `/initialize`

- **初期データは MySQL を通さずに読む。** mysqldump の `INSERT INTO ... VALUES (...),(...);` は
  小さなパーサで読める（文字列のエスケープ `\'` `\\` `\n`、`NULL`、数値）。
  ダンプの `TIME_ZONE`（ISUCON14 は `+00:00`）に合わせて時刻を解釈する
- パースは初回だけにし、結果をキャッシュする（gob の byte 列で持ち、`/initialize` のたびにデコードして新品を作る）
- **`/initialize` ではストアのポインタを差し替えない。** 並行するハンドラが古いポインタを掴んでいてデータ競合になる。
  ロックを取って中身のフィールドを入れ替える
- **起動時は、スナップショットがあればそれを読み、無ければ初期データを読む。** `/initialize` に依存しない
  （追試は再起動後に `/initialize` 無しで走りうる）

## 4. 永続化

**書き込みのたびにはディスクへ触らない**（遅い）。水準は `innodb_flush_log_at_trx_commit=0`
（1 秒ごとに fsync）と同じにする。ISUCON で定番のこの設定が通る以上、再起動試験はこの水準で通る。

- **定期スナップショット**: 変更があったとき（dirty フラグ）だけ、1 秒ごとに書く
  - ロックの中では値のコピーだけをする。エンコード（gob）と書き出しはロックの外でやる
  - 一時ファイルに書く → **fsync** → rename → **ディレクトリを fsync**。fsync しないと、ディスクへの書き出しが
    カーネル任せ（最大 30 秒ほど遅れる）になり、ハードリブートで失う幅が広がる
- **停止シグナルで同期的にダンプ**: `SIGTERM` / `SIGINT` / `SIGHUP` / **`SIGQUIT`** を受けたら、
  書き込みのロックを取ってからダンプし、終了する
  - ISUCON の unit は `ExecStop=/bin/kill -s QUIT $MAINPID` のことがある。Go は既定だと SIGQUIT で
    スタックを吐いて落ちるので、**必ず QUIT も拾う**
  - ダンプは数ミリ秒で終わる。systemd の停止待ち（既定 90 秒）に収まる
- スナップショットは `app.dir` の外（例: `/home/isucon/isuride-snapshot.gob`）に置く。deploy は `app.dir` を上書きで同期する
- 失いうる幅: 正常な再起動（systemctl reboot、EC2 の RebootInstances・Stop）は 0。
  プロセスだけが落ちた場合（kill -9・OOM）とハードリブートは最大 1 秒

## 5. 周辺の設定

- **systemd unit から `Requires=mysql.service` / `After=mysql.service` を外す**（`conf/<host>/etc/systemd/system/`）。
  MySQL が上がらなくてもアプリが起動するように
- **DB の遅さが隠していた上限に注意する。** 速くなると依頼が増え、別の上限に当たる。
  例: ISUCON14 のマッチングは 1 回の呼び出しで 1 件しか割り当てず、0.5 秒間隔なので秒間 2 件で詰まり、
  インメモリ化した直後に fail した（CODE 32: ライドが長時間マッチングされない）。1 回で全件を割り当てるよう直した
- インメモリ化の後は pt-query-digest が空になる（report.md で警告が出るが正常）。
  見るべきは Access log・Resources・CPU profile

## 6. 検証（採用する前に全部やる）

1. `bin/isuh bench` が pass する（スコアだけでなく、ベンチマーカーの整合性チェックが通ること）
2. **再起動試験**（`isuh verify-restart` が無ければ手で。ベンチが走っていない間に）
   1. API でデータを書く（オーナー登録 → 椅子登録 → 位置を 2 回送る、など）。
      書いた直後の読み取り API の応答を保存する
   2. **すぐに**再起動する（定期ダンプを待たず、シグナルでのダンプを試すため）。
      `sudo systemctl reboot` と、本番に近い `aws ec2 reboot-instances --instance-ids <id>` の両方
   3. 同じ Cookie で読み取り API を叩き、応答が完全に一致することを確かめる（`cmp`）
   4. アプリのログで、停止時の「ダンプした」と起動時の「スナップショットを読んだ（件数）」を確かめる
3. 再起動の後にベンチを回し、スコアが再現することを確かめる

**再起動試験の落とし穴**

- Cookie や保存した応答を `/tmp` に置かない。再起動で消える（ホームの下に置く）
- ISUCON14 のベンチは開始時に必ず `/api/initialize` を叩くので、ベンチを回すとデータが初期化される。
  永続化の確認はベンチではなく、API を直接叩いて行う
- 検証用に書いたデータとファイルは、終わったら片付ける
