# 頭打ちを疑うとき

「もう限界」と判断する前に、この手順で確かめる。誤って頭打ちと判断すると、残っている大きな伸びしろ
（多くはアルゴリズム・アプリの振る舞いの側）を試さずに終わる。

## 実例（ISUCON14 のリハーサル）

- 3 台とも CPU が張り付いたのを見て「頭打ち」と判断し、CPU を減らす変更を 6 つ続けた
  （GC 15% → 3.5%、スナップショットの間隔、JSON ライブラリ、ロック待ち −73% など）。どれもぶれ（±3%）の範囲だった
- 打開したのはマッチングの方針の変更（+8%）。「迎えの時間の短い順の貪欲法が最適」という前提を、それまで一度も試していなかった。
  この変更は CPU の仕事をむしろ増やした（座標の送信が 35 万件 → 37 万件）
- 途中で「変更したつもりが入っていなかった」ランを「効果なし」と誤判定していた（`git revert` の失敗の後にコミットしたら、ラン記録しか入っていなかった）
- 外部のレビュー（別のモデルにベンチのソースを読ませる）で、この誤りと、試していなかった前提が見つかった
- その後、「一番多いリクエスト（座標の送信）の遅延が律速」という見立て（外部のレビューも同じ見立て）を、
  感度の実験（その API に sleep を 5ms 足す）で確かめたら、スコアは落ちなかった。見立ては外れていた
- 仕様上の最短時間との比を時間帯別に出すと、序盤は 1.0 倍、終盤は 3.9 倍。ベンチマーカーのホスト自体が終盤に
  CPU の空き 2〜15% まで張り付いていて、スコアの上限はベンチ側で決まっていた（下の「ベンチマーカーのホスト」）
- 他チームの記事の手法（同じベンチのマシンで約 3% 上）を追試しても伸びず、差はぶれとサーバーの種類で説明がついた

## いつこの手順に入るか

- 続けて 3 つの変更が、ぶれの幅（SKILL.md「4. 採否を決める」）に収まった
- 「どのホストも張り付いている」「もう削るところがない」と感じた

## 1. 張り付き ≠ 律速

ISUCON のベンチは閉ループで、こちらが速くなるほどユーザー・負荷を増やす。終盤はどこかが必ず張り付く。
張り付いていることは、それがスコアを決めている証拠にならない。

### 感度の実験（わざと遅くする）

疑っている資源を、わざと少し悪くしてスコアの落ち方を見る。速くする変更より数行で書けて、1〜2 ランで判定できる。

- アプリの CPU → ハンドラで一定時間 CPU を回す（busy loop）。数 % ぶん使わせる
- レイテンシ → 一番多いエンドポイントに `time.Sleep` を数 ms 入れる
- nginx → `worker_processes` を 1 つ減らす

判定:
- スコアがほとんど落ちない → その資源は律速ではない。削っても伸びない。別の項（下の 2.）を疑う
- 大きく落ちる → 律速。削る価値がある

実験用のコミットは採用しない。測ったら revert する（コミットメッセージに「計測」と書く）。
revert の後は、実験のコードが消えたことを `git show --stat HEAD` と grep で確かめる（SKILL.md「4. 採否を決める」の落とし穴）。

### ベンチマーカーのホスト

手元でベンチマーカーを動かすリハーサル（`bench.runner: local`）では、ベンチマーカーのホストも資源の一つ。
閉ループのベンチは、こちらが速くなるほどユーザー・リクエストを増やすので、ベンチ自身が先に張り付くことがある。

- report.md の Resources で `（ベンチ）` のホストが飽和と出たら疑う
- このあいだは、サーバー側の改善はスコアに出にくい。ベンチの仕事を減らす変更（返す件数を減らす、プロトコルを変える等）が
  過大に良く見えるので、採否を本番に持ち込む前に割り引く
- 確かめ方: ベンチのホストを一時的に大きくして同じ sha を回す（費用が掛かるので人に確認）。スコアが上がればベンチ律速
- 本番のベンチは運営のマシンで動く。リハーサルの頭打ちが本番の頭打ちとは限らない

### クライアントから見た遅延

nginx の `request_time` やアプリの計測には、TLS の確立・中継（L4 のプロキシ等）・クライアント側の処理が入らない。
ベンチマーカーのホストから、接続を使い回して経路ごと（入口 / nginx に直接 / アプリに直接）に往復を測ると、
どの段で時間が増えているかが分かる。負荷を掛けていないときと、ベンチ中の両方で測って比べる。

## 2. スコアを式に分解して、どの項が止まっているかを見る

`docs/RULEBOOK.md` の「スコアの計算式」から、スコアを観測できる項の積・和に分解して書き出す。例（ISUCON14）:

```
スコア ≒ 完了数 × 1 件あたりの売上
完了数 ≒ 椅子の数 × (負荷走行の時間 ÷ 1 ライドの周期)
1 ライドの周期 = マッチ待ち ＋ 迎え ＋ 乗車 ＋ 評価・決済 ＋ 通知の遅れ
```

- 各項を毎ランで出す。ベンチの出力（最終集計・評価の内訳）と、アプリが持っているデータ
  （状態ごとの時刻など）から取れることが多い。スクリプトにしておき、スコアと 1 行に並べる
- 変更のたびに、スコアだけでなく項の動きを見る。「スコアは同じでも、ある項は良くなり別の項が悪くなった」が分かる
  （リハーサルでは、評価が下がったのに完了数が増えてスコアが上がった変更があった）
- 動いていない項が、次に攻めるところ。それがインフラで削れるものか、方針（割り当て・待ち・順序）で変わるものかを考える
- 時間の項は「仕様上の最短時間との比」でも出し、時間帯別（例: 10 秒ごと）に並べる。
  序盤から比が悪ければ仕組み（実装・プロトコル）の問題、負荷とともに悪化するなら容量の問題と切り分けられる
- 分解のスクリプトはアプリのリポジトリ（例: `tools/`）にコミットする。一時ディレクトリはセッションの整理で消える。
  出力の要約は `isuh bench --note` に残すと、`history.tsv` で後から比べられる

## 3. 前提を書き出して、安く試す

今の実装が置いている前提を箇条書きにする。例:「この割り当て方が最適」「この外部呼び出しは同期で仕方ない」
「この通知の間隔は効かない」。

- それぞれ、否定する最小の実験を考える。安いものから 1 つずつ試す
- 理屈で最適と考えたものほど、測っていないことが多い
- 定番の高速化も前提の一つ。リハーサルでは、高速版の JSON ライブラリがリクエストごとのスタック拡張で標準より遅く、
  HTTP/2 を外すとクライアント側は速くなったのに全体では 2 割落ちた。入れたら測り、効かなければ戻す

### ベンチのソースで「判定の窓」を読む

ワーニングやエラーを避けたいとき、推測で安全側に倒すとスコアを失う（リハーサルでは、完了直後の対象を一覧から
隠したら、依頼が減って 2〜3 割落ちた）。ベンチのソースで判定の条件を正確に読む:

- 何秒以内なら許すか、ベンチはどの時点で状態を切り替えるか（レスポンスを受け取った時か、送った時か）
- その条件の内側で、出せるものは出し、遅らせられるものは遅らせる。リハーサルでは、この形で該当のワーニングを
  約 150 件から 0 件にし、スコアは落とさなかった

## 4. 外からの目を入れる

別のエージェント・別のモデルに、ベンチマーカーのソースと現状（構成・やったこと・数字）を渡して、打開策と
「見立てが正しいか」を聞く。読むだけ（コードを変えない）にさせる。

- 渡すもの: 構成、ここまでの変更と各スコア、今の律速の見立て、ベンチマーカーのソースの場所、ラン記録の場所
- 返ってきた案は、根拠（ベンチのどこか）を確かめてから試す。効く理由が外れていても、実験のきっかけとして使う
- 効くのは「見落とし」の指摘（入れたつもりの変更が入っていない、試していない前提がある）。律速の見立てそのものは
  外れることがあるので、上の感度の実験で確かめてから方針にする

## 5. 判定は同じ sha で 3 回

このフェーズでは、ベンチの枠を使ってでも、基準の sha と候補の sha をそれぞれ 3 回ずつ回す。
「効果なし」と確定させる判断は、以降の方針を大きく変えるため。平均とぶれの幅で比べる。
