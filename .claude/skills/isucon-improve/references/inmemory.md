# DB を捨ててインメモリ化する

ISUCON14 のリハーサル（[isucon-harness#18](https://github.com/tmokmss/isucon-harness/issues/18) ）で、
MySQL を捨てて全状態をメモリに持つ実装に書き換え、2,034 → 82,363 まで伸ばした。
そのとき踏んだ落とし穴と判断をまとめる。

参照実装: ブランチ `rehearsal/isucon14` の `webapp/go/store.go`（ストア・永続化・シグナル）と
`webapp/go/initial_data.go`（mysqldump のパーサ）。ただしロックは全体で 1 つの簡略版で、
下の「ストアとロックの単位」（テーブル単位が既定）とは違う。永続化とインデックスの参考にする。

ISUCON では初手で MySQL を捨てる。インデックスや N+1 を 1 つずつ直すより先にやる
（リハーサルでは、インデックスを入れた 2,034 から、インメモリ化とマッチングの一括化で 52,919 に伸びた）。SKILL.md の
「0. 競技開始直後」の最後の手順がこれ。以降の改善（1 周 1 変更・計測・採否）は SKILL.md に従う。
インメモリ化は変更が大きいので 1 周で入れてよいが、必ず再起動試験まで通してから採用する。

## 0. 前提と例外

捨てるのが前提。DB が遅いことは ISUCON ではほぼ毎回の前提として扱い、計測で確かめてから決めることはしない
（CLAUDE.md の「計測せずに推測で最適化しない」の例外で、チームで決めた方針）。
ただし比較のため、初期状態のベンチは先に取っておく。

やめるのは次の場合だけ。

| 例外 | 代わりにやること |
|---|---|
| `docs/RULEBOOK.md`（当日マニュアル）が禁じている（特定のミドルウェアの利用、採点時に DB を見る等） | MySQL を残す。マニュアルに従う |
| 状態が大きすぎてメモリに持てない（4GB のうちアプリに使えるのは 2〜3GB 程度） | MySQL を残し、読み込みはメモリ、書き込みは順序を保った非同期（FIFO で 200ms ごとにまとめて書く等） |

- 状態を持つプロセスは 1 つだけにする。複数台で同じ状態を持つと、台同士の不整合と
  編集の競合が起きる。nginx は、状態を持つ 1 台にだけ振る
- CPU が足りなくなっても、状態を持つプロセスは 1 つのまま。他の台に nginx などの状態を持たない処理を逃がす

## 1. データ構造

ストアとロックの単位
- 行はテーブルごとの struct（元の models.go のもの）へのポインタで持ち、テーブルごとに map とインデックスをまとめる
- ロックはテーブルごとに 1 つ（`sync.RWMutex`）。これを既定にする
  - 大半の書き込みは 1 テーブルで完結する。全体で 1 つのロックにすると、それらまで直列になる
  - テーブルをまたぐ処理は、必要なテーブルのロックを全部取ってから処理し、終わってからまとめて放す（2 相ロック）。
    元のトランザクションと同じ原子性が得られる
- 読み込みは `RLock`、書き込みは `Lock`
- 行単位のロックは、同じテーブルの別々の行を頻繁に書き換えるとき（通知の既読フラグ、位置の更新等）に足す。
  map への追加・検索はテーブルのロック、行のフィールドは行のロック
- 全体で 1 つのロックは、全体の状態を見て決める処理（マッチングのような割り当て）だけに使う。普段の既定にはしない
- カウンタやフラグは atomic でよい（複数のフィールドを一緒に変えるときは不可）

デッドロックを防ぐ
- テーブルに順位を付け、ロックは必ず順位順に取る。全員が同じ順で取れば、待ちが循環しない
- 呼び出し側は `Lock()` を直接呼ばず、順位順に取る関数を必ず通す（順序の違反を書けなくする）

  ```go
  type table int

  const (
  	tUsers table = iota // 順位 = 取る順
  	tOwners
  	tChairs
  	tRides
  	tRideStatuses
  	tCoupons
  	nTables
  )

  var locks [nTables]sync.RWMutex

  // lockTables は書くテーブルと読むテーブルのロックを順位順に取り、放す関数を返す
  func lockTables(write, read []table) (unlock func()) {
  	var mode [nTables]int // 0: 取らない, 1: 読み, 2: 書き
  	for _, t := range read {
  		mode[t] = max(mode[t], 1)
  	}
  	for _, t := range write {
  		mode[t] = 2
  	}
  	for t := range nTables {
  		switch mode[t] {
  		case 1:
  			locks[t].RLock()
  		case 2:
  			locks[t].Lock()
  		}
  	}
  	return func() {
  		for t := nTables - 1; t >= 0; t-- {
  			switch mode[t] {
  			case 1:
  				locks[t].RUnlock()
  			case 2:
  				locks[t].Unlock()
  			}
  		}
  	}
  }

  // 例: ライドの作成（rides・ride_statuses・coupons に書き、users を読む）
  unlock := lockTables([]table{tRides, tRideStatuses, tCoupons}, []table{tUsers})
  defer unlock()
  ```

- 守る決まり（破るとデッドロックする）
  - 必要なロックは処理の最初にまとめて取る。途中で追加しない。途中で要るかもしれないテーブルは最初から含める
  - 読みから書きへ格上げしない。`RLock` を持ったまま `Lock` すると自分を待って止まる。書く可能性があれば最初から書きで取る
  - 再入しない。Go の mutex は同じ goroutine でも二重に取ると止まる。ロックを持った状態で呼ぶ補助関数は自分で取らず、
    名前で区別する（例: `latestStatusLocked`）
  - ロックを持ったまま、チャネルや他の goroutine の完了を待たない
  - 行単位のロックも同じ順序に載せる: テーブルのロック → 行のロック。同じテーブルの複数の行は ID の昇順
- 開発中の検出: `go test -race` はデッドロックを見つけない。順序の逆転は、開発中だけ `github.com/sasha-s/go-deadlock` に
  差し替えると報告される（使い方は `sync.RWMutex` と同じ）

ロックの中でやらないこと
- I/O（外部 API、ディスク、ログ出力）。外部呼び出しの間はロックを放し、戻ってから状態を確かめ直して書く
- 重い計算。計算はロックの外で行い、確定するときだけロックを取って前提が崩れていないかを確かめる
  （例: マッチングの候補の計算は外、割り当ての確定は「まだ空いているか」を確かめてから中）
- 「読んでから書く」処理を複数のロック区間に分けない（更新が失われる）
- ロックの外で使う値（レスポンスに詰める値）は、ロックの中でコピーしておく
- ロック待ちは pprof の mutex プロファイル（`runtime.SetMutexProfileFraction`）で見る。待ちが見えた箇所から細かくする

インデックス
- 元の SQL を 1 本ずつ書き出し、検索条件ごとに map / slice を 1 つ用意する

  | 元の SQL | メモリ上 |
  |---|---|
  | 主キー `WHERE id = ?` | `map[id]*Row` |
  | 一意キー `WHERE access_token = ?` | `map[token]*Row` |
  | 一意でないキー + 並び `WHERE user_id = ? ORDER BY created_at` | `map[userID][]*Row`（作成順に append すれば並べ替え不要） |
  | 同上 + `DESC LIMIT 1` | 同じ slice の末尾 |
  | 条件付きの一覧 `WHERE chair_id IS NULL ORDER BY created_at` | 専用の `[]*Row`（条件から外れたら取り除く） |
  | 集計 `SUM(...) GROUP BY x` | 集計結果そのもの `map[x]*Agg`（書き込みのたびに足し込む） |
  | 件数 `COUNT(*) WHERE code = ?` | `map[code]int` |
  | 時刻の範囲 `WHERE t BETWEEN ? AND ?` | 時刻順の slice を二分探索（`sort.Search`）。件数が少なければ全走査でよい |

- 複合キーは、区切り文字で連結した文字列（`userID + "\x00" + code`）か、struct をキーにする
- 1 つの行のポインタを全部のインデックスで共有する（コピーを持たない）。1 か所を書き換えれば全部に反映される
- インデックスの更新は `addRide` のような関数に集める（登録漏れを防ぐ）
- インデックスに使っているフィールドを後から書き換えるときは、古いキーの登録を消す
- 同じ時刻の行の並び（`ORDER BY` の同順位）は、挿入順 + ID で決める

履歴を全部持たない
- API が読むのが集約だけなら、集約だけを持つ
  - 例: `chair_locations` は全件を持たず、椅子ごとに「最新の位置・累計距離・最終更新時刻」だけを持つ。
    重い集計クエリ（slow query の 65%）が O(1) になった

## 2. レスポンスの互換（変えると失格）

レスポンスの構造体は元のまま使う。そのうえで、SQL と Go の挙動の差を 1 つずつ潰す。

- `nil` と空の slice の違い: 元が `var xs []T` に append する書き方なら、0 件のとき JSON は `null`。
  `[]T{}` にすると `[]` になり、形が変わる
- 並び順: `SELECT * FROM t` は主キー順（ULID なら作成順）。Go の map を回すと順序がばらばらになる。
  元の順序が不定だった箇所（元も map を回していた等）は不定のままでよい
- 時刻: `CURRENT_TIMESTAMP(6)` はマイクロ秒で丸まる。`time.Now().UTC().Truncate(time.Microsecond)` に揃える。
  `UnixMilli()` で返す値がずれないように
- `ON UPDATE CURRENT_TIMESTAMP`: 行が実際に変わったときだけ `updated_at` が進む。同じ値の UPDATE では進まない
- エラーの返し方: 一意制約の違反は元のコードでは 500 になる。同じステータスを返す
  （検証を先にしてから書く。元はトランザクションで巻き戻していた）
- 元が `/initialize` 後に `settings` を読んでいた値（決済の URL 等）もストアに持つ

## 3. 初期データと `/initialize`

- 初期データは MySQL を通さずに読む。mysqldump の `INSERT INTO ... VALUES (...),(...);` は
  小さなパーサで読める（文字列のエスケープ `\'` `\\` `\n`、`NULL`、数値）。
  ダンプの `TIME_ZONE`（ISUCON14 は `+00:00`）に合わせて時刻を解釈する
- パースは初回だけにし、結果をキャッシュする（gob の byte 列で持ち、`/initialize` のたびにデコードして新品を作る）
- `/initialize` ではストアのポインタを差し替えない。並行するハンドラが古いポインタを掴んでいてデータ競合になる。
  全テーブルの書きロックを順位順に取って（`lockTables(全テーブル, nil)`）、中身のフィールドを入れ替える
- 起動時は、スナップショットがあればそれを読み、無ければ初期データを読む。`/initialize` に依存しない
  （追試は再起動後に `/initialize` 無しで走りうる）

## 4. 永続化

書き込みのたびにはディスクへ触らない（遅い）。水準は `innodb_flush_log_at_trx_commit=0`
（1 秒ごとに fsync）と同じにする。ISUCON で定番のこの設定が通る以上、再起動試験はこの水準で通る。

- 定期スナップショット: 変更があったとき（dirty フラグ）だけ、1 秒ごとに書く
  - 全テーブルの読みロックを順位順に取り（`lockTables(nil, 全テーブル)`）、値のコピーだけをする。
    テーブルごとに別々に取ってコピーすると、テーブル間で食い違った状態が残る。エンコード（gob）と書き出しはロックの外でやる
  - 一時ファイルに書く → fsync → rename → ディレクトリを fsync。fsync しないと、ディスクへの書き出しが
    カーネル任せ（最大 30 秒ほど遅れる）になり、ハードリブートで失う幅が広がる
- 停止シグナルで同期的にダンプ: `SIGTERM` / `SIGINT` / `SIGHUP` / `SIGQUIT` を受けたら、
  全テーブルの書きロックを順位順に取ってから（以降の書き込みを止めて）ダンプし、終了する
  - ISUCON の unit は `ExecStop=/bin/kill -s QUIT $MAINPID` のことがある。Go は既定だと SIGQUIT で
    スタックを吐いて落ちるので、必ず QUIT も拾う
  - ダンプは数ミリ秒で終わる。systemd の停止待ち（既定 90 秒）に収まる
- スナップショットは `app.dir` の外（例: `/home/isucon/isuride-snapshot.gob`）に置く。deploy は `app.dir` を上書きで同期する
- 失いうる幅: 正常な再起動（systemctl reboot、EC2 の RebootInstances・Stop）は 0。
  プロセスだけが落ちた場合（kill -9・OOM）とハードリブートは最大 1 秒

## 5. 周辺の設定

- systemd unit から `Requires=mysql.service` / `After=mysql.service` を外す（`conf/<host>/etc/systemd/system/`）。
  MySQL が上がらなくてもアプリが起動するように
- DB の遅さが隠していた上限に注意する。速くなると依頼が増え、別の上限に当たる。
  例: ISUCON14 のマッチングは 1 回の呼び出しで 1 件しか割り当てず、0.5 秒間隔なので秒間 2 件で詰まり、
  インメモリ化した直後に fail した（CODE 32: ライドが長時間マッチングされない）。1 回で全件を割り当てるよう直した
- インメモリ化の後は pt-query-digest が空になる（report.md で警告が出るが正常）。
  見るべきは Access log・Resources・CPU profile

## 6. 検証（採用する前に全部やる）

1. `bin/isuh bench` が pass する（スコアだけでなく、ベンチマーカーの整合性チェックが通ること）
2. 再起動試験（`isuh verify-restart` が無ければ手で。ベンチが走っていない間に）
   1. API でデータを書く（オーナー登録 → 椅子登録 → 位置を 2 回送る、など）。
      書いた直後の読み取り API の応答を保存する
   2. すぐに再起動する（定期ダンプを待たず、シグナルでのダンプを試すため）。
      `sudo systemctl reboot` と、本番に近い `aws ec2 reboot-instances --instance-ids <id>` の両方
   3. 同じ Cookie で読み取り API を叩き、応答が完全に一致することを確かめる（`cmp`）
   4. アプリのログで、停止時の「ダンプした」と起動時の「スナップショットを読んだ（件数）」を確かめる
3. 再起動の後にベンチを回し、スコアが再現することを確かめる

再起動試験の落とし穴

- Cookie や保存した応答を `/tmp` に置かない。再起動で消える（ホームの下に置く）
- ISUCON14 のベンチは開始時に必ず `/api/initialize` を叩くので、ベンチを回すとデータが初期化される。
  永続化の確認はベンチではなく、API を直接叩いて行う
- 検証用に書いたデータとファイルは、終わったら片付ける
