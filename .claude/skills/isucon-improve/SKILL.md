# ISUCON の改善ループ

このリポジトリは ISUCON2026 専用で、アプリ（`webapp/`）・サーバの設定（`conf/<host>/`）・
ハーネス（`bin/isuh`）が 1 つにまとまっている。計測はすべて `isuh bench` が行う。
自分で ssh してログを見たり、サーバで設定を直接いじったりしない。

1 周 = 「report.md を読む → 1 つ直す → コミット → `isuh bench` → 採否を決める」。
1 周で直すのは 1 つだけ（2 つ同時に変えると、どちらが効いたか分からない）。

## 0. 競技開始直後に 1 回だけ（誰か 1 人がやる）

10:00 に始めて、10:05 にインメモリ化を始め、10:10 に初期状態のベンチを回す。サーバはスタック作成から約 3 分で SSH できる。

1. `bin/isuh portal whoami` でチーム名が出るか確かめる（65 なら人に Cookie を取り直してもらう）
2. テンプレートを取ってスタックを作る。確認は要らない。テンプレートはチーム固有のトークンを含むので、リポジトリの外に置き、中身を出力しない
   ```sh
   bin/isuh portal get /api/contestant/cloud_formation | node -e 'process.stdout.write(JSON.parse(require("fs").readFileSync(0,"utf8"))["1"])' > ~/.isucon/cfn.yaml
   aws cloudformation create-stack --profile tenjikai-dev --region ap-northeast-1 --stack-name tomooka-sandbox-isucon2026 --template-body file://$HOME/.isucon/cfn.yaml --capabilities CAPABILITY_IAM
   ```
3. 起動を待つ間に当日マニュアル（ポータルの `/docs`）を `docs/MANUAL.md` に保存し、下の「ルールブックを読む」を始める。台数とインスタンスタイプを人に報告する
4. `whoami` にサーバ一覧が出たら、各台の IP を `config.ts` の `setup.addresses` に入れ、コードだけ先に取り込んで main に push する（`bin/isuh setup --only ssh,apprepo`）
5. push した直後に、インメモリ化をサブエージェント 1 本に任せる（`isolation: "worktree"`、下の「初手で MySQL を捨てる」）。終わるまで他の改善を並べず、メインは `webapp/` に触らない
6. 残りを流す（`bin/isuh setup --only hosts,dotfiles,tools,logs,conf`）。`config.ts` の `app.*` と `hosts.*` を当日の値に直して push し、`bin/isuh bench --note "初期状態"` を回す

以下の「ルールブックを読む」「alpMatches を作る」はメインが並行して進める。「pprof を仕込む」は `webapp/` を触るので、インメモリ化のサブエージェントに含める。ルールブックを読む前に、コードを直さない。

### ルールブックを読む

CLAUDE.md §2・§3 は毎年共通の一般論。その年の条件は当日マニュアルとアプリの仕様書にしか無い。
ここを飛ばすと、やってよい変更の範囲もスコアの上げ方も推測になる。

1. 読む
   - 当日マニュアル — レギュレーションの追加・変更、追試（再起動後のベンチ）の手順と
     スコアの再現の基準、禁止事項
   - アプリの仕様書 — スコアの計算式（何が加点・減点か）、ベンチマーカーが検証する内容、
     エラーコードの意味、アルゴリズム（マッチング等）を変えてよい範囲
2. 要点を `docs/RULEBOOK.md` に書き出す。見出しは次の 4 つ。各項目に出典（マニュアルのどの節か）を付ける
   - 禁止事項（CLAUDE.md §2 に無いもの・より厳しいもの）
   - 追試の条件
   - スコアの計算式
   - レスポンスの形の制約（変えてよい部分・いけない部分）
3. CLAUDE.md の §3 の末尾に `@docs/RULEBOOK.md` の 1 行を足す（import。全エージェントが自動で読む）
4. コミットして main に入れる。並列で動いている他のエージェントは main を取り込む
- 当日マニュアルが CLAUDE.md のレギュレーションと矛盾したら、マニュアルを優先する。
  RULEBOOK.md に矛盾点を明記する（CLAUDE.md の本文は書き換えない）
- 改善の根拠には仕様を使う。スコアの計算式から、どの指標（成功数・レイテンシ・エラーの減点など）を
  上げるべきかを決める。ログだけから推測しない

### alpMatches を作る

`config.ts` の `metrics.alpMatches` が空だと、`/api/user/1` と `/api/user/2` が別の行に割れて
alp の集計が役に立たない（report.md の Access log 節に警告が出る）。

1. アプリのルーティング定義を読む（Go なら `webapp/go/main.go` 付近の `e.GET(...)` / `r.Get(...)` 等）
2. パスパラメータを含むルートごとに正規表現を書く。`:id` / `{id}` → `[^/]+`

   ```ts
   alpMatches: [
     "^/api/user/[^/]+$",
     "^/api/user/[^/]+/icon$",
     "^/api/competition/[^/]+/ranking$",
   ],
   ```
3. 長い（具体的な）パターンを先に書く。alp は最初に当たったものに寄せる
4. コミットする（`config.ts` はコミット対象）

### pprof を仕込む（Go）

```go
import (
	"net/http"
	_ "net/http/pprof"
)

func main() {
	go func() { _ = http.ListenAndServe("localhost:6060", nil) }()
	// ...
}
```

- `localhost` で待ち受ける（外に開かない。ハーネスは `hosts.app[0]` 上で curl する）
- `config.ts` の `metrics.pprofEnabled: true`。`pprofUrl` の `?seconds=N` はベンチの長さ（通常 60）に合わせる
- 本番の最後に外す（finalize #8 が確認する）

### 初手で MySQL を捨てる（インメモリ化）

ISUCON では初手で MySQL を捨て、アプリの状態をすべてメモリに持つ。インデックスや N+1 を
1 つずつ直すより先にやる（ISUCON14 のリハーサルでは、インデックスを入れた 2,034 から、インメモリ化とマッチングの一括化で 52,919 に伸びた）。
手順と勘所は `references/inmemory.md` を読んで従う。

1. 初期状態のベンチを取っておく（`bin/isuh bench --note "初期状態"`）。比較と、fail したときの切り分けに使う
2. インメモリ化して、`references/inmemory.md` の「検証」（ベンチの pass と再起動試験）まで通す
3. 以降の改善は、メモリ上の実装を前提に 1 周ずつ回す

- これは CLAUDE.md の「計測せずに推測で最適化しない」の例外で、チームで決めた方針。
  DB が遅いことは、ISUCON ではほぼ毎回の前提として扱う
- やめるのは、`docs/RULEBOOK.md`（当日マニュアル）が禁じている場合と、状態が大きすぎてメモリに持てない場合だけ
  （判断は `references/inmemory.md` の「0.」）

## 1. report.md を読む

最新のランは `bin/isuh history` の最後の行（run-id）。レポートは `runs/<run-id>/report.md`。
report.md だけ読めば判断できるように作ってある。生ファイル（`alp.txt` / `ptquery.txt` /
`cpu.pprof`）は、表で当たりを付けた後に深掘りするときだけ読む。

読む順番:

1. Summary — `status` が `pass` 以外なら、まず直す（「4. 採否を決める」の「失敗した」）
2. Resources — どのホストの何が詰まっているか。ここで方針が決まる
   - `isu1（CPU が飽和、主に mysqld）` → インメモリ化がまだなら、それが先（「0.」の「初手で MySQL を捨てる」）。
     MySQL を例外として残した場合だけ、Slow query を見る
   - `主に isuports`（アプリ）→ CPU profile と Access log を見る
   - `IO 待ちが重い` → DB のディスク（インデックス無し・`innodb_buffer_pool_size`・fsync）
   - どこも飽和していない → アプリの待ち（ロック・外部呼び出し・`sleep`）や nginx の設定を疑う
   - 張り付いていても、それが律速とは限らない。ベンチはこちらが速くなるほど負荷を上げるので、終盤はどこかが必ず張り付く。
     削っても伸びない変更が続いたら「5. 頭打ちを疑うとき」へ
   - 平均の CPU 使用率が低くても、「90% 以上の時間」が長ければ終盤は張り付いている
   - `（ベンチ）` と付いたホスト（ベンチマーカーを動かしている手元のホスト）が飽和と出たら、スコアがベンチの処理能力で
     頭打ちになっている可能性がある。サーバーを削っても伸びにくい。`references/plateau.md`「ベンチマーカーのホスト」へ
3. Slow query — MySQL を例外として残した場合だけ。`share` が大きい順に見る
   - `rows_examined_avg` が `rows_sent_avg` よりずっと大きい → インデックスが効いていない。
     `webapp/sql/` のスキーマに `ALTER TABLE ... ADD INDEX` / `CREATE INDEX` を足す
   - PostgreSQL（pg_stat_statements）では `blks_avg`（1 回あたりに読んだページ数）が `rows_avg` よりずっと大きいとき同じ
   - `calls` が桁違いに多い → N+1。アプリ側で JOIN / `IN (...)` にまとめる
   - 下の「上位の実例」はそのまま `EXPLAIN` に使える
4. Access log — `share`（合計時間の割合）が大きいエンドポイントから
   - `5xx` / `4xx` が出ている → 先にそれを直す（スコアの減点・失敗の原因）
   - `avg_bytes` が大きい → 帯域。画像などの静的ファイルは nginx に配らせる
5. CPU profile — アプリの中のどの関数か。`flat` が大きい関数を探す
6. Diff from previous run — 前回から何を変えたか（スコアの増減の理由付け）

## 2. 直す

- アプリは `webapp/` を、nginx / MySQL / systemd の設定は `conf/<host>/...` を編集する
  - サーバの `/etc` を直接編集しない。deploy で配られず、`deploy <古い sha>` でも戻らない
  - 参考: `setup/templates/`（nginx・mysqld のチューニングの定番）。計測で必要と分かってから写す
- スキーマの変更は、初期化（`/initialize` の SQL）と整合させる
  - `webapp/sql/` などバイナリ以外のファイルも deploy がサーバの `app.dir` へ上書きで配る。
    削除はされないので、ファイルを消したときはサーバ側でも消す（ファイル名を変えるより中身を書き換える方が安全）
- 直したらコミットする。配られるのは commit の中身だけ（未コミットの変更は警告されるが配られない）

```sh
git add webapp conf && git commit -m "users.email にインデックス（slow query 1 位、rows_examined 10000 → 1）"
```

コミットメッセージに根拠にした計測値を書く（どの表の何が悪かったか）。

ベンチの前に、意図した変更がコミットに入っていることを確かめる（`git show --stat HEAD`）。
前のコマンドの失敗に気づかずにコミットすると、変更の入っていないランを「効果なし」と誤判定する。
`isuh bench` も、前回のランと sha が違うのにアプリと `conf/` の中身が同じなら警告する。

新しいロジック（割り当て・並べ替えなど分岐の多い処理）は、関数単体だけでなく呼び出し側の分岐まで含めて
手元で動かしてから配る。総当たりと比べるテストが安くて確実。本番のアプリが panic で落ちたままベンチを回すと、
ランを丸ごと捨てることになる（report.md の Bench 節が空・スコア 0 なら、まずアプリのログで panic を探す）。

## 3. ベンチを回す

```sh
bin/isuh bench --note "users.email にインデックス"
```

- デプロイ → ベンチ → 計測 → report.md までを 1 本でやる。stdout はスコアだけ
- 他のエージェントがベンチ中ならロック待ちで止まる（同時に 2 本走らせない仕組み）。それで正常
- 数分かかる。完了したら stderr の `レポート: runs/<run-id>/report.md` を読む

| 終了コード | 意味 | 次にやること |
|---|---|---|
| 0 | 完走 | report.md を読んで採否を決める |
| 10 | ロックが取れない（誰かが長く握っている） | 保持者が表示される。待つか、その人に確認 |
| 20 | デプロイ失敗（ビルドエラー・起動しない） | stderr のエラーを直す |
| 30 | 検証ゲート失敗 | 壊れている。直す |
| 40 | ベンチ失敗 | report.md の Bench 節を全文読む |

## 4. 採否を決める

report.md の Summary に前回比・ベスト比が出る。ハーネスは良し悪しを判定しない。

- スコアのブレは数 % 〜 10 % ある。1 回の小さな増減で判断しない。迷ったら同じ sha でもう 1 回回す
  （`bin/isuh bench <sha> --note "再計測"`）
- ぶれの幅は、`runs/history.tsv` で同じ sha のまま 2 回以上 pass したランの (最大 − 最小) ÷ 平均 で見積もる。
  普段は 1 ランで回し、再計測したランが貯まるたびに見直す。プロファイルの取得など条件の違うランは除く。
  この幅に収まった差は「効果なし」ではなく「判定できない」。ISUCON14 のリハーサルでは多くが 2〜4%、ときどき 10% 近くあった
- 良くなった → そのまま次の周へ
- 悪くなった・変わらない → 戻す。コミットを revert してから次へ

  ```sh
  git revert --no-edit HEAD        # 戻したものも履歴に残す
  bin/isuh deploy                  # サーバも戻す（ビルドはキャッシュされるので速い。ベンチ中ならロックを待つ）
  ```

  `runs/history.tsv` は追跡されていて、ベンチのたびに書き換わる。未コミットのまま revert すると失敗し、
  ラン記録を含むコミットを revert すると衝突する。先にラン記録をコミットし、衝突したら revert をやめて
  `git checkout <戻したい sha> -- <ファイル>` で戻す。どちらでも、戻ったことを `git show --stat HEAD` で確かめる
  ラン記録は `git add runs` で `runs/<run-id>/` ごとコミットし、main へ取り込む。`history.tsv` が取り込みで衝突したら、両方の行を残す
- 失敗した（status が fail / error）→ Bench 節を全文読み、整合性チェックで落ちたなら
  レスポンスが変わっていないか確認する（下の禁止事項）

スコアの一覧は `bin/isuh history`（ベストに `*`、前回からの差）。

## 5. 頭打ちを疑うとき

続けて 3 つの変更がぶれの幅に収まった、どのホストも張り付いて削るところがないと感じた ——
このとき「もう限界」と判断する前に、`references/plateau.md` の手順で確かめる。要点:

- 張り付きは律速の証拠ではない。疑っている資源をわざと悪くして（CPU を回す・sleep を入れる）、スコアの落ち方で律速かを判定する
- スコアを観測できる項（例: 完了数・周期の内訳）に分解し、毎ランで並べる。動いていない項を攻める
- 実装の前提（「この割り当て方が最適」など）を書き出し、安い実験で否定を試みる
- 別のエージェント・モデルにベンチのソースと現状を渡して、見立てを聞く
- このフェーズの判定は、同じ sha で 3 回ずつ回した平均で行う
- ベンチマーカーのホスト自体が上限になっていないか（手元でベンチを動かすリハーサルで起きる）

## やってはいけないこと（失格・事故）

詳細は CLAUDE.md §2・§3 と `docs/RULEBOOK.md`（当日マニュアルの要点。こちらが優先）。改善で踏みやすいもの:

- レスポンスの形を変えない。JSON のキーの追加・削除・型の変更、HTML の DOM、JS / CSS / 画像の中身。
  「使っていないフィールドを返さない」も不可
- `/initialize` に頼らない。キャッシュのウォームアップを initialize の中だけでやると、
  再起動後の追試（initialize 無し）で壊れる。起動時にも温める
- オンメモリ化・キャッシュは、再起動後もデータが取れること。ベンチで書かれたデータが
  再起動で消える実装は失格。DB に書いてからキャッシュする
- 起動順に依存しない。アプリが DB より先に上がっても落ちない（接続のリトライ）
- 計測せずに推測で最適化しない。根拠の無い変更は、効いたかどうかも判断できない

## 並列で作業するとき

前提: 実装は並列にできるが、計測は直列。ベンチはロックで 1 本ずつしか走らない
（1 回 約 1.5 分: deploy 数秒 + ベンチ + 回収）。1 つの改善の実装は数分〜10 分かかるので、
ベンチの枠 1 つで数本の実装を回せる。実装の間にベンチを遊ばせないために並列にする。

並列にしてよい場面
- 独立した改善（触るエンドポイント・ファイルが分かれる）
- 同じボトルネックへの複数の案（A/B）。スコアのブレ（数 %〜10 %）があるので、1 案につき 2 回ずつ測る。
  3 案なら 6 回・約 9 分ベンチの枠を占めることを見込む
- 結果だけ欲しい調査（ロック待ちの調査、データの分布の集計など）。メインの文脈を汚さない

直列にする場面
- 土台を作る変更（初手のインメモリ化、構成の変更など）。他の全部がその上に乗るので、終わるまで並列にしない
- 同じファイルに集中する変更（インメモリ化の後のストアやロックの周り）。並列にすると衝突する
- ベンチの枠が埋まっているとき（計測待ちが伸びるだけ）

回し方（メインのセッション = コーディネータ）
1. メインが report.md を読み、独立した仮説を 2〜3 個に絞る（CLAUDE.md §5: 同時に 2〜3 レーンまで。判断と取り込みが詰まるため）
2. 仮説ごとに worktree のサブエージェントを立てる。渡す指示に書くこと:
   - 根拠にした計測値（report.md のどの表の何）
   - 触ってよい範囲（エンドポイント・ファイル）と、触らない範囲
   - このスキルの 1 周（直す → コミット → `isuh bench <ref>` → 採否の材料をまとめる）を回して、スコアと根拠を返すこと
   - サブエージェントは会話の文脈を知らない。禁止事項は CLAUDE.md とこのスキルにあるので、読むよう書く
3. メインが結果を見て、良かったものを main に取り込む
4. 他のエージェントは main を取り込んでから測り直す。効果は足し算にならない
   （A を入れるとボトルネックが移り、B の効き方が変わる）。main より古い土台で測った結果で採否を決めない

サーバに触るのはロックを取る経路だけ
- `isuh bench` と `isuh deploy` はどちらもロックを取る。それ以外でサーバを変えない
  （ssh での直接編集・`systemctl restart`・再起動）。並列のレーンのベンチを壊す
- 再起動試験のようにサーバを再起動する作業は、他のレーンに声をかけて止めてからやる
- `isuh bench <ref>` はそのブランチの ref を渡す。ロックで直列化されるので、計測は混ざらない
